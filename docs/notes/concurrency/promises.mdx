# Promises

## Promise state transitions

- Sequential: non-overlapping in duration
- Concurrent: overlapping in duration

**Source of parallelism: Hardware**

**Concurrency managed by: Operating system and `Lwt`**

## OS and I/O

Your program never touches the hardware directly
- So the OS has to help move bytes acorss the hardware/software boundary

Your prorgam asks OS to move bytes by making **system calls** to functions by OS API

### Channel
- A **channel** is a unidirectional stream of bytes mediated by OS between a program and I/O device

*Unidirectional: program -> device, or device -> prorgam*

*Stream: accepets/delivers data in order, like water through type*

## Async I/O

In `Lwt`, *non-blocking* I/O functions let the caller continue without waiting for the requested I/O to finish

- Ex. Netflix wants to be reading many files and distributing to many viewers over the network

### Async With Promises

`Lwt` I/O functions return promises!

**Non-blocking**:

**Two ways to use promises**

1. **Wait** - Decide that there is one main promise that you need, and tell `Lwt`
: when that promise is resolved, you want the result

2. **Schedule** - Decide that when a give promise is duiflled, you already know what work you want to do with the result. Give `Lwt` 
a function that it can run on your behalf

#### Wait call `run`
```ocaml

```

- Call `run` from your prorgam to start `Lwt` main loop aka scheduler
- `run p` will not return until `p` is resolved

#### Schedule: Call `map`

```ocaml

(** [map f p ] schedules callback [f] to run after [p] is fufilled *)
````

## Definitions

In `Lwt`, a *promise* is a `ref`, a value that is permitted to mutate at
most *once*. When created, it is like an empty box that contains nothing. We say that the 
promise is `pending`. Eventually, a promise can be `fufilled`, which is like putting something
into the box. Instead of being fulfille, the promise can instead be `rejected`, in which case the box is filled with
an `exception`. 

In either case, `fufilled` or `rejected`, we say that the promise is `resolved`. Regardless
of whether the promise is resolved or rejected, once the box is filled, 
its contents never change.

:::info
- The client code will need to **access** promises to make use of concurrency.
This means querying promises whether they are `resolved` or `pending` and then make use of the resolved
values
- The library and OS code that implements concurrency will need to **mutate** the promise: either fufill it or reject it
:::

:::danger
Client code **cannot** mutate promises
:::

From this, we will use an abstraction called a **resolver**.

### Implementing Promises

```ocaml
(** A signature for Lwt-style promises, with better names. *)
module type PROMISE = sig
  type 'a state =
    | Pending
    | Fulfilled of 'a
    | Rejected of exn

  type 'a promise

  type 'a resolver

  (** [make ()] is a new promise and resolver. The promise is pending. *)
  val make : unit -> 'a promise * 'a resolver

  (** [return x] is a new promise that is already fulfilled with value
      [x]. *)
  val return : 'a -> 'a promise

  (** [state p] is the state of the promise. *)
  val state : 'a promise -> 'a state

  (** [fulfill r x] fulfills the promise [p] associated with [r] with
      value [x], meaning that [state p] will become [Fulfilled x].
      Requires: [p] is pending. *)
  val fulfill : 'a resolver -> 'a -> unit

  (** [reject r x] rejects the promise [p] associated with [r] with
      exception [x], meaning that [state p] will become [Rejected x].
      Requires: [p] is pending. *)
  val reject : 'a resolver -> exn -> unit
end
```

To implement this interface , we can make a representation type of `'a promise` be a 
`ref` ro a `state`

```ocaml
type 'a state = Pending | Fulfilled of 'a | Rejected of exn
type 'a promise = 'a state ref
```

For a representation type of the resolver, we'll do something a little clever. It will simply be an `'a promise`

In this way, the OS is the **producer**: responsible for computing a value then resolving a promise
- It needs to write, or mutate, to the promise

The program is the **consumer**: responsible for consuming the value if/when it becomes available
- It needs to read, or access the value from the promise
- It should ***never*** write to the promise 

This way, a consumer is ***prohibited from writing** while the OS has access to the resolver
